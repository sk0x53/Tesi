This has been one of the most crucial points of the whole work.
First of all I have tried to instrument the forkserver function directly inline.
This approach presents many problems. The biggest difficulty is the fact that a forkserver needs some library functions 
to work properly:
\begin{itemize}
    \item \texttt{read/write} to implement the communication protocol with the fuzzer.
    \item \texttt{fork/waitpid} to implement the forkserver main logic.
\end{itemize}
These functions could be part of the target binary (if the binary already uses these functions) or not.
In the best case, the binary already uses these functions and they are available. 
In this case, a call to these functions could be instrumented at any time, taking into consideration the type of 
linking with which the binary has been compiled.
\begin{itemize}
    \item In case of \textit{Static Linking}, the function instructions are already inside the target application, 
        because the linker inserted them during compilation. So a call to these functions could be inserted by finding 
        the function address and then instrumenting a call instruction to that address.
    \item In case of \textit{Dynamic Linking}, the function instructions are not inside the target application when 
        it is launched, but the function addresses are dynamically resolved by the dynamic linker as needed. 
        In this case, two new sections must be used (the \texttt{.plt} and \texttt{.got} sections, as seen in 
        \cref{sec:loading_relocations}).
\end{itemize}

If the functions required by the forkserver are part of the target binary, their calls can be easily instrumented. 
Depending on whether the binary is statically or dynamically linked, this can be done either by finding the address 
of the function and calling it directly, or by finding the address of its .plt entry and calling that, 
leaving the dynamic linker to resolve the function. 
The problem arises when the original binary does not include these functions. 
In this case, it is almost impossible to modify the .plt and .got sections to include the new functions 
while preserving the binary's layout and correctness in the general case. In fact, in some exceptional cases 
padding may provide enough space in the .got section for a new entry, but this cannot be assumed in general. 
Therefore, this first approach has been completely discarded.
Since the forkserver is more complex than a simple shared map update, due to the presence of many checks on 
environment variables and communication with the fuzzer, 
the best approach is to inject the compiled forkserver code into the target through \textit{Shared Object Injection}.
In order to achieve Shared Object Injection, the \textit{.dynamic} section of the target binary must be modified.
In particular:
\begin{itemize}
    \item A \textit{DT\_NEEDED} entry is added with the name of the shared object to be injected. \footnote{In reality 
        the shared object name is a string that is written into the \textit{.dynstr} section, and the 
        \textit{.dynamic} section specifies the offset of the string written into \textit{.dynstr}.}
    \item A \textit{RUNPATH} entry is added containing the path where the actual shared object is saved.
\end{itemize}
\footnote{
    The injection could also be done with the LD\_PRELOAD environment variable. 
    This variable tells the dynamic linker to add the specified libraries as dependencies of the executable.
    The problem is that at each execution the variable must be reset with the name of the shared object.
    By adding the DT\_NEEDED dependency instead, the dependency becomes persistent.
}\\
The shared object injected into the target binary contains the code of the forkserver, which must be executed 
before the main of the binary.
In order for a function of a shared object injected into a binary to be executed before the main, 
that function must be declared as a ``constructor''.
As stated in \cref{sec:loading_relocations}, by declaring a function as a constructor, its address is 
placed inside the \textit{.init\_array} section and executed before the actual start of the executable's main.
When an executable has some dependencies, the dynamic linker executes the \textit{.init} section and the functions 
contained in the \textit{.init\_array} section before actually starting the main of the executable.\footnote{
    The .init section is the legacy version of the .init\_array section. 
}
In \cref{fig:dl_sub2} the execution flow of the dynamic linker can be seen as it initializes the dynamic dependencies of a target binary that 
has the dynamic dependencies shown in \cref{fig:dl_sub1}.
\begin{enumerate}
    \item The dynamic linker searches for \textit{DT\_NEEDED} entries of the target binary. When a dependency is found, it maps the library 
        into a loaded \gls{VMA} of the process associated with the target binary being executed.
    \item For each library found previously, the dynamic linker executes each function found in the \textit{.init\_array} 
        section of that shared object.
    \item When the dynamic linker finishes, the \texttt{\_start} function is executed, and it in turn executes \texttt{\_\_libc\_start\_main}, 
        which executes all the functions in the \textit{.init\_array} of the target binary.
\end{enumerate}

problem of instrumenting the forkserver so that it is executed before the main.
